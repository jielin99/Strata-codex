数据来源是 `results/08-gr-down.md` 和 `results/08-gr-down/` 里的 `timing.tsv`、`decode.tsv`、`choice.txt`、`gr-*.txt`、`ev-*.txt`、`gap.txt`、

证据等级：✅ 已验证、⚠️ 推断、⬜ 未验证。每组 3 段、每段 9 个请求；ms/token = 生成总毫秒 ÷ 生成总 token。

## 1. 结论
1. ✅ **生成快约 7.4%（tok/s），回答不变，已进日常配置**：
   - 每 token 113.48 → 105.68 ms（−6.9%）。三对相邻段都是 B 快：1-A/2-B 108.45 → 107.10，4-A/3-B 115.36 → 104.52，5-A/6-B 116.62 → 105.43。
   - 每段的 ms/token 还随草稿接受率变（1-A 的接受率 0.558 最高，所以这一对差得少）。每窗口 verify（9 个请求，按窗口数加权）更稳：
     A 223.2、223.7、225.5 ms，B 203.1、207.6、209.8 ms，每个 B 段都比每个 A 段少。
   - 按 T 回归（每段 2 个贪心加 9 个请求，按窗口数加权）：A 126.2 + 30.4·T，B 111.3 + 30.2·T，T=3 时 217.2 → 201.8 ms（−15.4 ms）。
     斜率不变，省下的是每窗口固定的一块。
   - ⚠️ 和 `gr_bench` 一致：T=3 524.8 → 377.9 µs（−147 µs），每窗口 96 次 hc 读，约省 14 ms。
   - 草稿每窗口 A 25.6、25.7、25.4 ms，B 23.5、24.5、24.3 ms（草稿层也走同一个 hc 读）。草稿接受率 0.534、0.540。
   - q1/q2/q3 的生成 tok/s 中位数 11.4 → 12.2、7.8 → 8.4、8.1 → 8.5；首 token 中位数 3.09 → 2.88、2.58 → 2.44、2.82 → 2.69 s。
   - 回答：`v2`、`r128`、`r64` 的逐位核对四条标准都通过（两边都正常退出、各 33 行、`fc` 退出码 0、无差异）；12 个 `gr-*.txt` 里每个 T 的校验和都相同，
     也和开发机、06、07 的相同；两个贪心提示词 6 段哈希全同，也和 07 的相同。
   - 手册第 5 节的四个条件开发机逐条核对过：选出了 `v2`；6 段都完成，`timing.tsv` 54 行（每段 9 个）；哈希全同；三对都是 B 快。
     日常配置 `env` 现在有 `STRATA_MMVQ_Q6_SWAR`、`STRATA_Q2_SWAR`、`STRATA_GR_UP_EPI`、`STRATA_GR_DOWN_V2`（`config-change.json`）。
2. ✅ **按规则选的是 `v2`**：W 539.2 → 382.3 µs（−29%）；`r128` 392.7，`r64` 460.3。
   - ⚠️ 三个新变体的差别在噪声以内。140T 上 `gr_bench` 偶尔有一个点慢 150–270 µs：`v2` 第 2 轮 T=3 559.9（另两轮 377.9、349.4），
     `r64` 第 1、2 轮 T=4 617.2、546.5（第 3 轮 395.9），`r128` 第 1、2 轮 T=2 477.3、508.3（第 3 轮 309.5），`base` 也有（T=2 三轮 461.3、534.5、621.1）。
     `r64` 的 W 偏高，就是因为 T=4 有两个慢点。
   - `STRATA_GR_DOWN_ROWS` 不用，留作没人用的 opt-in。
3. ✅ **140T 上 hc 读的各内核**（`ev-*.txt`，各跑一次，µs）：

   | | T=3 base | T=3 v2 | T=6 base | T=6 v2 |

   | norm | 25.0 | 22.2 | 36.1 | 34.0 |

   - down 少了 58–60%。现在最大的是 up（T=3 占 51%）。
   - 同样 6.55 MB 的 BF16 权重（`hc_*_down`、`hc_*_up` 都是 10240×320），T=3 时 up 约 37 GB/s，down（v2）约 58 GB/s。
   - ⚠️ 单次的事件计时也有慢点：`v2` 的 up 在 T=1、2 是 217.8、229.7，`base` 是 127.1、153.6，可两次跑的 up 是同一份代码；`base` 的 T=4、5 也偏高

## 2. 分阶段计时（7-P，只看比例）
- ✅ 这次 PROFILE 统计 545 个窗口，生成统计 544 个，只多 1 个读提示词的窗口（01 多 7–9 个）。平均 T 2.62，每窗口 1.88 个 token，
  241.37 ms/窗口 = verify 217.06 + 草稿 24.19（草稿占 10.0%）。
- 各块（ms/窗口，占 GPU 各阶段合计 212.06 ms 的比例；权重按 `results/01-decode-bound/tensors.tsv` 算）：

  | 块 | ms/窗口 | 占比 | 实际读取速率 |

  | hc 读 96 次 + 路由 48 次 | 44.69 | 21.1% | 1,392 MB/窗口，31 GB/s |
  | GDN 递推 | 4.74 | 2.2% | |
  | 其余 | 0.99 | 0.5% | |

- 这份数字的限制：
  - ⚠️ PROFILE 本身让窗口变慢：它的 verify 是 217.06 ms（T 2.62），而 B 组的回归在 T=2.62 是 190.4 ms，多约 14%。
    打点用一个主机线程一直写时钟（`verify_kernels.dp.cpp:2552-2556`），占着一个 CPU 核。
  - ✅ 阶段边界会把时间算到相邻阶段：`shared+quant` 只有 0.47 ms/窗口，等于共享专家每窗口 120.9 MB 的权重按 257 GB/s 读完，
    是实测设备读取速率（约 72 GB/s，`results/01-decode-bound/bw-before.txt:4-8`）的 3.5 倍，不可能。至少约 1.2 ms 被算进了别的阶段，⬜ 算进了哪个没查。
  - 所以按块的比例（约 40% / 37% / 21%）可以用，单个阶段的数字至少有 1 ms 量级的误差。

## 3. 下一步的线索（都还没测，各自要单独写计划）
1. ⚠️ **路由段约 16 ms/窗口，离下限最远**：
   - `hc-read1+router` 减去 `hc-read0`：GDN 层每层 636 − 315 µs，QSA 层 622 − 248 µs，48 层合计约 16.0 ms/窗口（占 7.6%）。
     两次 hc 读是同一个函数、同样的形状（`verify.cpp:982-1003`；read0 是 `gr_read_group(0, pending, …)`，read1 是 `:1286` 的 `gr_read_group(1, true, …)`）。
   - 这一段除了 read1，还有：路由 GEMV（`bf16_gemv_fp32_mmvf_multi`，512×2560 BF16）；取前 10（`native_router_top10_multi`，每个 token 一个 256 线程的工作组，
     `native_router.dp.cpp:269-280`）；`resident_plan`（一个 128 线程的工作组，`verify_kernels.dp.cpp:2069`、`:2387-2388`）。
   - 路由权重每窗口 125.8 MB，按 72 GB/s 读只要约 1.7 ms。
