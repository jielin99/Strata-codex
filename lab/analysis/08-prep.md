# 08 的依据：hc down 开关、放弃的两个变体、140T 编译目标的寄存器溢出普查（开发机，2026-10-16）

证据等级：✅ 已验证、⚠️ 推断、⬜ 未验证。开发机 = UHD 730（Xe-LP），oneAPI 2025.3 容器，带引擎的链接选项（除法、开方正确舍入）。
「140T 编译目标」= 同一编译器以 `-device arl-h` AOT 编译、导出 ISA（不是在 140T 上跑）。方案经用户同意（Codex 讨论后修正），见 `analysis/07-gr-up.md` 第 3 节。

## 1. 候选：`STRATA_GR_DOWN_V2=1`（功能分支 `0408d916`，默认关）
- 原因：✅ hc 读的 down 内核（`gr_down_sliced_kernel`）在 140T 编译目标上有寄存器溢出，IGC 的两次编译分别 1,216、1,600 字节。
  它同时保留一行的 4 段 16 字节权重和 8 个 token 的累加器；Xe-LPG 每个线程 128 个 32 字节寄存器，SIMD32 下每个变量占 4 个。
- 改法：token 数做成模板参数（只留 T 个累加器）；权重段的循环放在 token 循环外面（同时只留一段）。每个 token 仍是 0 + 段 0 + 段 1 + 段 2 + 段 3，
  然后同样两步 xor、写同一个部分和位置。`STRATA_GR_DOWN_ROWS=64|128` 再把一片的 324 行分给多个工作组（Codex 的建议）。
- ✅ 140T 编译目标：新内核 T=1、2、4、6 都有不溢出的版本，T=3 最少 0（另一次编译 224 字节），T=8 最多 640 字节。
- ✅ 逐位相同（UHD 730）：`gr_bench` T=1–6 的校验和开关前后相同，也和 06、07 在 140T 上的相同；`gr_apply_parity` 32 种情况相同。
  覆盖 v2 单独、加 ROWS 64 / 128、有没有 `STRATA_GR_UP_EPI`。
- ✅ UHD 730 `gr_bench`（EPI 开）：hc 读 T=3 730.8 → 677.0 µs（−7.4%），T=6 1,189.4 → 1,087.8 µs（−8.5%）；ROWS 64、128 和 v2 单独差不多。
- ⚠️ 140T 上的收益不能从 UHD 730 推（07 的教训）。08 先在 140T 上比较 base、v2、ROWS 128、ROWS 64，按加权时间选一个，再做端到端。

## 2. 放弃的两个变体
- **Q4_K/Q5_K 激活字节和预计算（`STRATA_MMVQ_KSUM`）**：✅ 输出逐字节相同，但 UHD 730 上每个形状、每个列数都更慢（+6%～+61%）。
  宽内核一个工作组只有 4 行，每组预计算要读 NCOLS × 2,560 字节的激活（3 列 7.7 KB），和它自己读的权重（Q4_K 约 5.8 KB）同一量级。
  改成全局预计算要每个 GEMV 多一个图节点和一块缓冲区；Codex 修正后的估计最多每窗口约 3 ms。按停止条件不做，代码没有提交。
- **reduce 先读 8 个再加（`STRATA_GR_REDUCE_LA`）**：✅ 140T 编译目标上的指令和原 reduce 基本相同（send 都是 13 条），UHD 730 只快 2%。不做。

## 3. 140T 编译目标的寄存器溢出普查（18 个和生成有关的内核文件）
| 内核（默认路径） | 溢出（字节） | 说明 |
|---|---:|---|
| hc down `gr_down_sliced` | 1,216 / 1,600 | 08 的候选 |
| MoE gate/up `gu_port<18 / 21 / 22, 8>`（IQ3_XXS / IQ3_S / IQ2_S） | 1,120–1,984 | `<16, 8>`、`<17, 8>`（IQ2_XXS / IQ2_XS）不溢出 |
| MoE down `down_port<142, 8>`（Q2 SWAR）/ `<20, 8>`（IQ4_NL） | 256 / 0 | |
| GDN 递推 `gdn_step_norm_multi` | 各变体最多 6,720–10,336（个别为 0） | ⚠️ 01 的 PROFILE 里 GDN rec 约 7 ms/窗口 |
| QSA `qsa_decode_attn_batch` / `qsa_block_topk` | 5,824 / 11,840 | 01 的 PROFILE 里 QSA attention 约 0.1 ms/窗口 |
| `quantize_q8_0`、QSA indexer append | 3,168 / 3,040 | |
| 稠密 GEMV 默认的宽内核 | 0 | `analysis/02` |

- ✅ **溢出不一定慢**：06 的 `moe_lab`（Q2 开）里，10 种 gate/up + down 类型组合在 T=1–4 的速率（同一 T、同一类型 3 次的中位数）都在 27–35 GB/s
  （单次最低 24.3，`moe-4-on.tsv:28`），不溢出的 IQ2_XXS/XS 并不比溢出的 IQ3_S 快。
- ⚠️ **待验证的假设**：MoE 在 140T 上可能卡在访存方式（比如同时在途的读不够多）。不同类型的字节数、解码指令、寄存器占用和访问方式是一起变的，
  相近的 GB/s 不能把这些因素分开，所以还不能排除解码计算或溢出。
- ⚠️ **MoE 是下一个最大的线索**：稠密宽内核在 1 列时，Q4_K、Q5_K、Q6_K（SWAR）、IQ4_XS 的大矩阵有 44–66 GB/s，
  但 IQ3_S 只有 22–26 GB/s（`results/02-mmvq-q6k/compare.tsv`，base 列；Q6_K 用 nosat 列）；MoE 约 27–35 GB/s。
  MoE 每窗口约 67 ms；假设能到 IQ4_XS 那样的约 45 GB/s（T=3 时各类型中位数的平均是 31.6 GB/s），每窗口约省 20 ms——这只是假设下的估算。原因没查，要单独一轮（不进 08）。

## 4. 为什么 08 末尾加一段 PROFILE
- 01 的 PROFILE 每个请求统计的窗口比生成窗口多 7–9 个（`results/01-decode-bound/3-P-decode.txt`：例如生成 52 个窗口，PROFILE 统计 59 个），
  多出的是读提示词的窗口，所以稠密等阶段的时间被放大（qkv 一段 56 ms，微基准估计约 16 ms）。现在没有一份干净的、引擎里的分阶段时间。
- 08 末尾用一个生成约 1,000 个 token 的请求跑一次 PROFILE。提示词窗口仍在统计里，只是占比小（实际比例看这一段的生成窗口数和 PROFILE 的窗口数），
  所以得到的是近似的阶段比例。只用来看比例（打点本身也会改变执行），不参与任何决定。
- 只靠提示词窗口混入，也不足以解释 01 的 PROFILE 和微基准之间的全部差距（Codex 外审意见）；这一段测完再对。
