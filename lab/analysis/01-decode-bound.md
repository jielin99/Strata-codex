# 01 的分析（开发机，2026-10-15）

数据来源是 `results/01-decode-bound.md` 和 `results/01-decode-bound/` 下的文件（下面简称「数据目录」）。
文中的计算都在开发机上直接从这些文件算出。证据等级：✅ 已验证（文件里的数字，或者代码）、⚠️ 推断、⬜ 未验证。

## 1. 结论（摘要）

1. ⚠️ **生成速度不是卡在内存带宽上**。verify 窗口按字节数折算，只用到实测读带宽（72 GB/s）的约 20–40%。
   单个稠密 GEMV 阶段只有 12–20 GB/s，MoE 专家阶段的上限约 23 GB/s。时间主要花在内核本身。
2. ✅ **投机解码对 q2、q3 的收益很小**。草稿接受率：q1 约 0.75，q2 约 0.43，q3 约 0.47。按全部请求合计，每个 token
   约 130–147 ms；单 token 窗口约 159–180 ms。也就是说，投机解码平均只快 18% 左右；⚠️ 推断 q2、q3 更少。
3. ✅ **MTP 草稿只占每个窗口的约 10%**（约 29 ms / 292 ms），不是计划里写的 66 ms（约 20%）。候选 B 的优先级要降低。
4. ✅ **这台机器在 1 小时内越跑越慢**（同样的配置，前后差 9–15%），读带宽却没有变化。以后做 A/B 对照，必须短段交替进行。

## 2. 每个窗口读多少字节

（例如 `blk.0.hc_attn_down.weight` 是 6553600 字节 = 10240×320×2）。⚠️ 代码里有 hc 的 q8 路径（`verify.cpp` 中的
`a.q8_down = wd[half]->hc_q8`），这次走的是哪一条没有确认，所以 hc 按 q8（下限）到 BF16（上限）给出区间。

## 4. 投机解码

| | q1 | q2 | q3 | 来源 |
|---|---:|---:|---:|---|
| 接受数 / 提供数（6 段平均） | 约 67 / 88 | 约 48 / 111 | 约 51 / 108 | `timing.tsv` |
| 接受率 | 0.75–0.78 | 0.41–0.47 | 0.43–0.49 | 同上 |

| 段 | 平均 T | tokens/窗口 | ms/窗口 | ms/token | T=1 窗口的 verify（ms） |
|---|---:|---:|---:|---:|---|
| 2-T | 3.34 | 2.24 | 292.3 | 130.5 | 159.9、158.6 |
| 5-T | 3.19 | 2.16 | 317.6 | 146.9 | 178.7、180.4 |

- ⚠️ 推断：每多一行 verify，耗时增加约 44 ms（(261.6−159.2)/(3.34−1)），另外每个窗口还有约 29 ms 的草稿。q2、q3 每行只接受约 0.45 个 token，
  多出的 token 每个约花 100 ms，比单 token 窗口的 159 ms 便宜，但便宜得不多。窗口取多长最划算，要靠实测。
- 候选 C（投机参数）不需要改代码，只调 `--spec`、`--spec-min-p`、suffix lookup 的配置就能测。目标是 ms/token。

## 5. 机器状态漂移

| | 前 | 后 | 变化 | 来源 |
|---|---:|---:|---:|---|
| q1 生成 tok/s（1-N → 6-N） | 9.9 | 8.4 | −15% | 结论文件的总表 |
| verify T=1（2-T → 5-T） | 159.2 | 179.6 | +13% | decode.txt |
| verify 多 token（2-T → 5-T） | 261.6 | 285.2 | +9% | decode.txt |
| 读带宽 device（前 → 后） | 72.28 | 72.71 | 不变 | bw-*.txt |

- ⚠️ 推断：可能是 GPU 频率或温度。读带宽没变，而生成变慢，这也说明生成卡在计算侧，不在带宽侧（和第 1 条一致）。⬜ 频率没有测。
- 3 种开关之间的比较被漂移盖住了：T 段和相邻的 N 段差不多（10.4 对 9.9，8.7 对 8.4），说明 `STRATA_DECODE_TIMING` 没有可见的成本。
  P 段介于两者之间，看不出它自己的成本。
