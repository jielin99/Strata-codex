# 10 的判断：140T 上 MoE 和稠密 GEMV 内核的拆分计时（开发机，2026-10-17）

数据来源是 `results/10-kern-ablate.md` 和 `results/10-kern-ablate/` 里的 `ka-1.tsv`、`ka-2.tsv`、`check.txt`、`ka-exit.txt`、`stderr.txt`、`build.txt`。
140T 的数字都是开发机从这两份 `tsv` 直接算的（每个数是 5 轮的中位数，单位 µs，`kern_ablate 5 100`）。「相对 `base`」是两次平均之比，括号里是两次各自的比。
证据等级：✅ 已验证、⚠️ 推断、⬜ 未验证。

**读法**（`analysis/10-prep.md` 第 4 节）：诊断版本改变了编出的代码（寄存器、依赖、溢出，第 5 节有例子），去掉一步省下的时间不是那一步的精确占比，
也不能单独排除某种限制。下面 ✅ 只用于测得的时间关系，「瓶颈在哪」一类的解读都是 ⚠️。

## 1. 数据可用
- ✅ 两次退出码 0，stderr 为空；58 行、键集合、`same` 列全部符合手册；两次之间 58 个 `checksum` 0 处不同。复制的 `base` 在所有权重拷贝上和引擎逐位相同，
  候选 `slm`、`pf2`、`pf4` 和 `base` 逐位相同。
- ✅ 噪声比开发机大得多：单次的 `spread`（5 轮的极差 ÷ 中位数）1.0%–61.7%，两次之间同一行最多差 19.3%（Q4_K `base` 1 列）。
  所以下面只用两次同向、幅度明显大于两次之差的结果。

## 2. MoE gate/up 的单 entry 路径（25 个专家，各 1 个 entry）
| 版本 | IQ3_S（13 层） | IQ2_XXS（9 层） |
|---|---:|---:|
| `base` | 958.4 µs | 527.6 µs |
| `now`（不读权重） | −35.8%（−39.5 / −32.0） | −27.6%（−28.4 / −26.7） |
| `nogrid`（不查码本） | −29.9%（−30.9 / −28.8） | −19.8%（−21.3 / −18.5） |
| `noact`（不读激活） | −6.6%（−7.5 / −5.7） | −11.1%（−8.6 / −13.5） |
| `nosign`（不做符号） | −5.9%（−12.3 / +0.6） | −3.2%（−3.4 / −3.1） |
| **`slm`（码本放共享内存，逐位相同）** | **−19.6%（−25.0 / −14.0）** | **−13.2%（−11.9 / −14.4）** |

1. ✅ 去掉一步最多省三成多：不读权重 27.6–35.8%，不查码本 19.8–29.9%，不读激活 6.6–11.1%，不做符号 3.2–5.9%。
   完全不读权重时，时间还剩 64–72%（`now` 的等效权重吞吐 53–60 GB/s，`base` 36–41 GB/s）。
   ⚠️ 推断：这个内核不只是被显存带宽卡住，和 09 的「读同一个专家只快 4–13%」方向一致；诊断版本也改了编出的代码，不能据此排除带宽的影响。
2. ✅ **`slm` 在这个工具里逐位相同，IQ3_S 快 14–25%（两次平均 19.6%），IQ2_XXS 快 12–14%**。
   - 09 的开关在单 entry 情形（`T1`、`G10x1`：10 个组各 1 个 entry，`results/09-moe-grid/mp-*.tsv` 的 gate/up 阶段，3 轮中位数，关 → 开）：
     IQ3_S `G10x1` −2.8% / −1.5%、`T1` −4.8% / −10.0%；IQ3_XXS `G10x1` −12.2% / −13.3%（两种 down 各一行）。
   - ✅ 代码不同（读代码）：09 的 `native_gu_sg_kernel` 把单个 entry 也改走 `row_dot_multi<…, 1>`（`iq_kernels.dp.cpp:1935`）；
     10 的 `slm` 保持默认路径的 `row_dot_lanes` → `vec_dot_*`（`:1858`），只把查表换成共享内存。
   - ⚠️ 但两轮同时变了别的：10 个组对 25 个组、1 个 token 对 4 个 token 的激活、引擎的完整内核对省掉组循环和 entry 分派的复制版、
     主机计时（含提交、等待、SwiGLU、量化）对单个内核的 GPU 事件计时。**还没有在同一个工具里隔离写法的影响**，所以「10 的写法省得多」只是推断。
3. ⚠️ **条件外推（只是量级，不是预期收益）**：IQ3_XXS 按 IQ3_S 的 −19.6%、IQ2_XS 按 IQ2_XXS 的 −13.2% 赋值，乘 09 的 T=3 各格式 gate/up 时间
   （关，读各自的专家，3 轮中位数）和层数：IQ3_XXS 1.02、IQ3_S 2.53、IQ2_XXS 0.85、IQ2_XS 0.94，合计 5.33 ms/窗口，
   占 08 的 241.37 ms/窗口（`analysis/08-gr-down.md` 第 2 节）的 2.2%。IQ2_S 不算（09 里它变慢 23%）。
   这里一起外推了：两种没测的格式（IQ2_XS 的码本是 512 个 64 位项，和 IQ2_XXS 不同）、多 entry 的组、gate/up 阶段里不会变的 SwiGLU 和量化。

## 3. 稠密 Q6_K（SWAR，2560 → 10240）
| 列数 | `base` µs | `noact`（不读激活） | `now`（不读权重） | `pf2` | `pf4` |
|---:|---:|---:|---:|---:|---:|
| 1 | 349.2 | −15.5%（295.1 µs） | −73.5% | +9.8% | +369.4% |
| 2 | 368.1 | −19.0%（298.1 µs） | −52.8% | +21.0% | +12.9% |
| 3 | 415.9 | −28.3%（298.3 µs） | −17.5% | +14.2% | +6.6% |
| 4 | 446.2 | −30.8%（309.0 µs） | +33.8% | +20.8% | +17.8% |

1. ✅ **不读激活时，时间几乎不随列数增加**（295 → 309 µs；`base` 349 → 446 µs）。⚠️ 推断：每多一列的成本和激活这一步（读取、占寄存器）有关；
   `noact` 的溢出也比 `base` 少（第 5 节），不能当作精确占比。
2. ✅ 1 列时不读权重快 73.5%（`base` 等效约 61 GB/s）；3 列时 `now` 只快 17.5%，4 列反而慢 33.8%。⚠️ 推断：后者是编出的代码变了（第 5 节，`now` 的溢出随列数增加）。
3. ✅ **两个候选都更慢，不用**：`pf2` +9.8% 到 +21.0%，`pf4` +6.6% 到 +369.4%。

## 4. 稠密 Q4_K（2560 → 10240）
| 列数 | `base` µs | `noones`（不算激活和） | `noact` | `now` | 引擎 µs |
|---:|---:|---:|---:|---:|---:|
| 1 | 257.5 | −15.0%（−9.8 / −19.4） | +9.0%（+22.0 / −1.9） | −48.2% | 257.9 |
| 2 | 446.8 | −15.2%（−11.9 / −18.3） | −40.4% | −49.6% | 332.9 |
| 3 | 393.1 | −11.6%（−6.6 / −15.9） | −14.1% | −22.4% | 448.6 |
| 4 | 472.8 | −13.1%（−9.5 / −16.5） | −14.0% | −17.7% | 496.9 |

1. ✅ **`noones` 四种列数都快 12–15%，两次同向**。去掉的是每行每列重算的激活和（与权重无关）。⚠️ 08 准备时因为开发机上更慢而放弃的「激活和每窗口算一次」，
   在 140T 上值得重新做成候选（替换后还要加读取，省不到这么多）。
2. ✅ 复制的 `base` 2 列比 3 列还慢（446.8 对 393.1 µs），引擎 2 列 332.9 µs。⚠️ 推断：复制版在这一点上编出的代码比引擎差（第 5 节，2 列的溢出最多），所以 2 列的比例不用。

## 5. 新线索：64 位寻址的链接选项（开发机核对）
引擎和 `kern_ablate` 都带链接选项 `-ze-opt-greater-than-4GB-buffer-required`（`sycl/CMakeLists.txt:59-68`），要求内核按 64 位地址（stateless）访问。
不带它时，编译器可以把能追溯到指针参数的访问改成「分配起点 + 32 位偏移」的方式（✅ 汇编里看到：MoE 内核读指针表，不带选项是 `a32`，带选项是 `a64`）。
加它的原因是 A770 上读超过 4 GiB 处的专家时出错（`docs/INTEL.md:718-726`）；文档写着「速度代价没测」。

1. ✅ **开发机容器里的编译器（oneAPI 2025.3）为 140T 编译目标（`-device arl-h`，128 个寄存器，SIMD32）编出的工具复制版，带选项时指令多、溢出多**。
   每个内核汇编的 `//.instCount` 和溢出字节数（不是运行时的溢出流量）：

   | 内核（1 / 2 / 3 / 4 列） | 指令数：不带 → 带 | 溢出字节：带选项（引擎的设置） | 溢出字节：不带 |
   |---|---|---|---|
   | Q6_K `base` | 1,800 / 877 / 1,000 / 1,128 → 2,295 / 1,235 / 1,471 / 1,708（+27.5% 到 +51.4%） | 4,128 / 2,208 / 2,368 / 2,528 | 3,072 / 1,536 / 1,568 / 1,728 |
   | Q6_K `noact` | | 928 / 832 / 736 / 704 | 192 / 832 / 512 / 576 |
   | Q6_K `now` | | 416 / 2,464 / 5,984 / 8,640 | 448 / 0 / 3,840 / 7,456 |
   | Q6_K `pf4` | | 8,096 / 4,160 / 4,512 / 5,344 | 5,856 / 3,008 / 4,800 / 8,416 |
   | Q4_K `base` | 1,227 / 1,819 / 963 / 1,208 → 2,031 / 2,927 / 1,558 / 1,902（+57.5% 到 +65.5%） | 1,504 / 2,912 / 1,632 / 2,048 | 0 / 480 / 448 / 576 |
   | Q4_K `noact` | | 1,536 / 0 / 0 / 224 | 0 / 0 / 0 / 0 |
   | MoE `base` IQ3_S | 885 → 1,102（+24.5%） | 第一次编译 544，重编后最终 64 | 0 |
   | MoE `base` IQ2_XXS | 730 → 859（+17.7%） | 0 | 0 |

   - ⚠️ 几处反常和溢出对得上：Q6_K `now` 的溢出随列数涨到 8.6 KB，时间也从 −73.5% 变成 +33.8%；`pf4` 1 列溢出 8.1 KB，慢 4.7 倍；
     Q4_K `base` 2 列溢出最多（2.9 KB），也正好比 3 列慢；Q4_K `noact` 2–3 列溢出 0，2 列快 40%。也有对不上的（Q4_K `noones` 3–4 列溢出比 `base` 多，却更快）。
   - ✅ 140T 上用的是笔记本驱动（32.0.101.8826）运行时编译的代码；⬜ 那里实际的指令数和溢出没看，可能和容器的编译器不同。
2. ✅ **开发机核显上，去掉这个选项，引擎的稠密内核快 8–24%，MoE 的耗时差在 1% 以内，保存的输出全部相同**
   （UHD 730，`kern_ablate 3 20`，同一份目标文件链接两次，按带 / 不带 / 不带 / 带交替各跑 2 次；同一种编译两次之间最多差 0.8%）：
   - 引擎自己的内核（两次平均）：Q4_K 1–4 列 −7.6%、−23.8%、−16.5%、−17.4%；Q6_K −8.1%、−14.3%、−16.5%、−12.5%；MoE gate/up IQ3_S −0.3%、IQ2_XXS −0.9%。
   - 4 次运行保存的 58 个 `checksum` 全部相同；要求逐位核对的 20 行 `same` 每次都是 1，其余 38 行是 `-`（诊断版本不核对）。
     工具内的逐位核对覆盖所有权重拷贝，跨编译比较的 `checksum` 只覆盖工具选定的输出，两者范围不同。
   - ✅ 读代码：MoE 的专家权重地址是从内存里读出来的（`grp_ptr[g]`，`iq_kernels.dp.cpp:1900`），这部分读取本来就是 64 位；
     但指针表、激活、输出的访问会随这个选项变（上面的 `a32` / `a64`），所以 MoE 内核整体也可能受影响。开发机上耗时只差 1% 以内；⬜ 140T 上没测。
   - ⚠️ 开发机的比例不能推到 140T（09 的教训）。
3. ⚠️ **条件外推**：08 的稠密 GEMV 77.60 ms/窗口是 GPU 各阶段合计（212.06 ms）的 36.6%、整个窗口（241.37 ms，含草稿）的 32.2%。
   如果 140T 上稠密也快 7.6–23.8%，每窗口省 5.9–18.5 ms，约 2.4–7.7%。hc 读、路由、注意力等其他内核的变化没算，也没测。
4. **引擎不能直接去掉这个选项**。已经找到的、要处理的地方（以后真要做时，审查的标准是「每次访问的整个区间相对它所在分配的起点」，不只是参数指针的起点）：
   - ✅ 专家缓存是一整块分配（`expert_cache.cpp:650-651`、`:718-719`；`:809` 返回块内的指针），08 实测 39.94–39.95 GiB（`results/08-gr-down/startup.tsv`）。
     本 SYCL 版本没有分段 / 虚拟内存的路径（`expert_cache.cpp:12`、`vmm.cpp:11-16`）。
   - ✅ 缓存的检查内核传入的是起点，但内部访问整个缓存（`sycl/include/strata/sycl_queue.hpp:180-193`）；参数偏移为 0 也会访问到 4 GiB 以外。
   - ✅ 读提示词的路径把常驻专家的指针（`prefill.cpp:4174`）传给反量化内核（`iq_kernels.dp.cpp:4455`、`:4555`、`:4603` 的内核直接接收权重指针）；A770 上出错的就是这条路径。
   - ✅ 主机镜像按每块最多 2 GiB 分配（`gguf_expert_source.cpp:166-189`），08 实测总量 0.02–0.03 GiB。
   - ⬜ 读提示词的缓冲、借用缓存尾部时的指针、要把缓存拆成多块时各处「单一起点」的假设（例如 `verify_kernels.dp.cpp:2196`）都还没审完；
     oneMKL 自带的内核不受这个链接选项控制（`gemm.dp.cpp:709-724` 另有保护）。

## 6. 结论
1. 140T 上 MoE gate/up 去掉任何一步最多省三成多；10 的 `slm` 写法在工具里逐位相同、单 entry 快 13–20%（两次平均）。和 09 的差别是不是来自写法，还没在同一工具里确认。
   做成引擎开关的收益按条件外推只是 2% 左右的量级，不是预期值。
2. 140T 上 Q6_K 不读激活时时间几乎不随列数增加；Q4_K 不算激活和快 12–15%；两个 Q6_K 预读候选都更慢，不用。
3. 新线索：引擎的 64 位寻址选项让工具复制版的稠密内核多 27.5–65.5% 的指令、溢出也多；开发机上去掉它，引擎的稠密内核快 8–24%，输出不变。
   140T 上的代价没测；引擎要去掉它，先得处理近 40 GiB 的整块专家缓存和直接读它的内核。

## 7. 下一步（需要你决定）
1. **在 140T 上测 64 位寻址的代价**（不改引擎）：`kern_ablate`、`gr_bench`、`moe_probe` 各编一次目标文件、链接两次（只差这个选项，其余选项和日常环境开关相同），
   两版都先预热，再按带 / 不带 / 不带 / 带交替跑，比较时间和正确性。
   - ✅ 外审读代码核对：三个工具的每块分配都远小于 4 GiB（`kern_ablate` 最大 21,504,000 字节，`gr_bench` 6,553,600 字节，`moe_probe` 的专家每块最大
     2,329,600 字节、各自独立分配），不带选项读得对。这只说明工具能安全地测，不说明引擎能去掉选项。
   - 三个工具的计时口径不同（`gr_bench` 反复用同一套权重，`moe_probe` 含主机等待，`kern_ablate` 的引擎行含标记之间的间隙），比例不能直接当端到端收益。
   - `now` 的伪权重由地址参与生成（`kern_ablate.cpp:87-88`），两种编译的诊断行 `checksum` 可能因地址不同而不同，不能判成读错。
   - 同时开发机按第 5 节第 4 条的标准审查引擎。代价大，再定引擎怎么改（默认关，逐位相同，端到端核对）。
2. **MoE gate/up 用 10 的 `slm` 写法做成引擎开关**（IQ3_XXS、IQ3_S、IQ2_XXS、IQ2_XS）：保留现有 4 个 / 2 个 entry 一起算的分派（`iq_kernels.dp.cpp:1839-1858`），
   只让剩下的单个 entry 走「`row_dot_lanes` → `vec_dot_*` + 共享内存码本」，新内核默认关。在 140T 上用 `moe_probe` 和端到端测。
3. **Q4_K/Q5_K 的激活和每窗口算一次**（逐位相同），在 140T 上和现状比。
