# 10 的判断：140T 上 MoE 和稠密 GEMV 内核的拆分计时（开发机，2026-10-17）

数据来源是 `results/10-kern-ablate.md` 和 `results/10-kern-ablate/` 里的 `ka-1.tsv`、`ka-2.tsv`、`check.txt`、`ka-exit.txt`、`stderr.txt`、`build.txt`。
140T 的数字都是开发机从这两份 `tsv` 直接算的（每个数是 5 轮的中位数，单位 µs，`kern_ablate 5 100`）。「相对 `base`」是两次平均之比，括号里是两次各自的比。
证据等级：✅ 已验证、⚠️ 推断、⬜ 未验证。

## 1. 数据可用
- ✅ 两次退出码 0，stderr 为空；58 行、键集合、`same` 列全部符合手册；两次之间 58 个 `checksum` 0 处不同。复制的 `base` 在所有权重拷贝上和引擎逐位相同，
  候选 `slm`、`pf2`、`pf4` 和 `base` 逐位相同。
- ✅ 噪声比开发机大得多：单次的 `spread`（5 轮的极差 ÷ 中位数）1.0%–61.7%，两次之间同一行最多差 19.3%（Q4_K `base` 1 列）。
  所以下面只用两次同向、幅度明显大于两次之差的结果。

## 2. MoE gate/up 的单 entry 路径（25 个专家，各 1 个 entry）
| 版本 | IQ3_S（13 层） | IQ2_XXS（9 层） |
|---|---:|---:|
| `base` | 958.4 µs | 527.6 µs |
| `now`（不读权重） | −35.8%（−39.5 / −32.0） | −27.6%（−28.4 / −26.7） |
| `nogrid`（不查码本） | −29.9%（−30.9 / −28.8） | −19.8%（−21.3 / −18.5） |
| `noact`（不读激活） | −6.6%（−7.5 / −5.7） | −11.1%（−8.6 / −13.5） |
| `nosign`（不做符号） | −5.9%（−12.3 / +0.6） | −3.2%（−3.4 / −3.1） |
| **`slm`（码本放共享内存，逐位相同）** | **−19.6%（−25.0 / −14.0）** | **−13.2%（−11.9 / −14.4）** |

1. ⚠️ **没有单一的瓶颈**：去掉一步最多省三成多（不读权重 28–36%，不查码本 20–30%）；完全不读权重，时间还剩 64–72%，所以不是被显存带宽卡住，
   和 09 的「读同一个专家只快 4–13%」一致。
   等效权重吞吐 `base` 约 36–41 GB/s，`now` 也只有 53–60 GB/s。
2. ✅ **10 的 `slm` 写法在 140T 上有效，09 的开关在单 entry 上几乎没有效果**。09 的单 entry 情形（`T1`、`G10x1`：10 个组各 1 个 entry，`results/09-moe-grid/mp-*.tsv`
   gate/up 阶段，3 轮中位数，关 → 开）：IQ3_S `G10x1` −2.8% / −1.5%、`T1` −4.8% / −10.0%（两种 down 各一行）。
   两者的区别（读代码）：09 的 `native_gu_sg_kernel` 把单个 entry 也改走 `row_dot_multi<…, 1>`（两个半和）；10 的 `slm` 保持引擎原来的
   `row_dot_lanes` → `vec_dot_*` 写法，只把查表的地址换成共享内存。⚠️ 推断：两种写法编出的代码不同，10 的写法在 140T 上省得多。
3. ⚠️ 估算（粗）：如果 IQ3_XXS、IQ3_S、IQ2_XXS、IQ2_XS 的 gate/up 都用 10 的写法（IQ2_S 不用，09 里它变慢 23%），按 09 的 T=3 各格式 gate/up 时间、
   层数和上表的比例，每窗口约省 4–5 ms，端到端约 2%。IQ3_XXS、IQ2_XS 在 10 里没测，多 entry 的组（09 的路径）也没在 10 里测。

## 3. 稠密 Q6_K（SWAR，2560 → 10240）
| 列数 | `base` µs | `noact`（不读激活） | `now`（不读权重） | `pf2` | `pf4` |
|---:|---:|---:|---:|---:|---:|
| 1 | 349.2 | −15.5%（295.1 µs） | −73.5% | +9.8% | +369.4% |
| 2 | 368.1 | −19.0%（298.1 µs） | −52.8% | +21.0% | +12.9% |
| 3 | 415.9 | −28.3%（298.3 µs） | −17.5% | +14.2% | +6.6% |
| 4 | 446.2 | −30.8%（309.0 µs） | +33.8% | +20.8% | +17.8% |

1. ✅ **不读激活时，时间几乎不随列数增加**（295 → 309 µs；`base` 349 → 446 µs）。⚠️ 推断：每多一列的成本主要在激活这一步（读、占寄存器），不在权重。
2. ✅ 1 列时不读权重快 73.5%：1 列主要卡在读权重（`base` 等效约 61 GB/s）；3 列时 `now` 只快 17.5%，4 列反而慢 33.8%（编出的代码变了，见第 5 节）。
3. ✅ **两个候选都更慢，不用**：`pf2` +9.8% 到 +21.0%，`pf4` +6.6% 到 +369.4%。

## 4. 稠密 Q4_K（2560 → 10240）
| 列数 | `base` µs | `noones`（不算激活和） | `noact` | `now` | 引擎 µs |
|---:|---:|---:|---:|---:|---:|
| 1 | 257.5 | −15.0%（−9.8 / −19.4） | +9.0%（+22.0 / −1.9） | −48.2% | 257.9 |
| 2 | 446.8 | −15.2%（−11.9 / −18.3） | −40.4% | −49.6% | 332.9 |
| 3 | 393.1 | −11.6%（−6.6 / −15.9） | −14.1% | −22.4% | 448.6 |
| 4 | 472.8 | −13.1%（−9.5 / −16.5） | −14.0% | −17.7% | 496.9 |

1. ✅ **`noones` 四种列数都快 12–15%，两次同向**。去掉的是每行每列重算的激活和（与权重无关）。⚠️ 08 准备时因为开发机上更慢而放弃的「激活和每窗口算一次」，
   在 140T 上值得重新做成候选（替换后还要加读取，省不到这么多）。
2. ✅ 复制的 `base` 2 列比 3 列还慢（446.8 对 393.1 µs），引擎 2 列 332.9 µs。复制版在这一点上编出的代码比引擎差（第 5 节），所以 2 列的比例不用。

## 5. 新线索：寄存器溢出和 64 位寻址（开发机核对，140T 的编译目标）
引擎和 `kern_ablate` 都带链接选项 `-ze-opt-greater-than-4GB-buffer-required`（`sycl/CMakeLists.txt:59-68`）：内核的指针参数全部按 64 位地址访问。
加它的原因是 A770 上读超过 4 GiB 处的专家时出错（`docs/INTEL.md:718-726`）；文档写着「速度代价没测」。

1. ✅ **140T 编译目标（`-device arl-h`，128 个寄存器，SIMD32）上，稠密内核的溢出很多**。开发机容器里的编译器（oneAPI 2025.3）编 `kern_ablate.cpp`，
   导出汇编里的溢出字节数（带 / 不带这个选项）：

   | 内核（1 / 2 / 3 / 4 列） | 带选项（引擎的设置） | 不带 |
   |---|---|---|
   | Q6_K `base` | 4,128 / 2,208 / 2,368 / 2,528 | 3,072 / 1,536 / 1,568 / 1,728 |
   | Q6_K `noact` | 928 / 832 / 736 / 704 | 192 / 832 / 512 / 576 |
   | Q6_K `now` | 416 / 2,464 / 5,984 / 8,640 | 448 / 0 / 3,840 / 7,456 |
   | Q6_K `pf4` | 8,096 / 4,160 / 4,512 / 5,344 | 5,856 / 3,008 / 4,800 / 8,416 |
   | Q4_K `base` | 1,504 / 2,912 / 1,632 / 2,048 | 0 / 480 / 448 / 576 |
   | Q4_K `noact` | 1,536 / 0 / 0 / 224 | 0 / 0 / 0 / 0 |
   | MoE `base`（IQ3_S；IQ2_XXS） | 64 或 544（编了两次）；0 | 0；0 |

   - 带选项时，这些 `base` 内核的汇编指令行数多 19–68%（MoE 19–27%，Q6_K 38–68%，Q4_K 61–67%；静态计数，含溢出代码）。
   - ⚠️ 几处反常和溢出对得上：Q6_K `now` 的溢出随列数涨到 8.6 KB，时间也从 −73.5% 变成 +33.8%；`pf4` 1 列溢出 8.1 KB，慢 4.7 倍；
     Q4_K `base` 2 列溢出最多（2.9 KB），也正好比 3 列慢；Q4_K `noact` 2–3 列溢出 0，2 列快 40%。也有对不上的（Q4_K `noones` 3–4 列溢出比 `base` 多，却更快）。
   - ⬜ 140T 上实际用的是笔记本驱动（32.0.101.8826）运行时编译出的代码，溢出数可能不同。
2. ✅ **开发机核显上，去掉这个选项，稠密内核快 7–24%，MoE 不变，结果逐位相同**（UHD 730，`kern_ablate 3 20`，同一份目标文件链接两次，各跑一次）：
   - 引擎自己的内核：Q4_K 1–4 列 −7.4%、−23.9%、−16.5%、−17.5%；Q6_K −8.2%、−14.3%、−16.6%、−12.5%；MoE gate/up IQ3_S −0.3%、IQ2_XXS −0.9%。
   - 58 行的 `checksum` 两种编译全部相同，`same` 列全部为 1。
   - ✅ 读代码：MoE 的专家权重地址是从内存里读出来的（`grp_ptr[g]`，`iq_kernels.dp.cpp:1900`），本来就按 64 位访问，所以这个选项对它影响小；
     稠密内核的权重、激活、输出都是指针参数，受这个选项影响。
   - ⚠️ 开发机的比例不能推到 140T（09 的教训）。同一份工具在开发机上的 `base` 和 10 准备时相差 0.2% 以内（Q4_K 1 列 1,491.7 对 1,494.4 µs，
     Q6_K 1,646.6 对 1,647.4 µs），所以这 7–24% 不是开发机的噪声。
3. ⚠️ 如果 140T 上也有相近的差别：稠密约占每窗口的 37%（`analysis/08-gr-down.md`），只算稠密，粗算端到端约 3–9%；hc 读、路由、注意力等其他吃指针参数的内核可能也受影响，没测。
4. ⬜ 引擎不能直接去掉这个选项：专家缓存是一整块（或预留的一整段地址）超过 4 GiB 的显存（`expert_cache.cpp:435`、`:650-651`），读提示词的路径有内核以指针参数读里面的专家
   （A770 上出错的就是这条路径）。要去掉，得先查清哪些内核会拿到距离分配起点超过 4 GiB 的指针，再决定是拆分配、还是只对一部分内核去掉。没查。

## 6. 结论
1. 140T 上 MoE gate/up 读权重、查码本各占三成左右，不是被显存带宽卡住；10 的 `slm` 写法逐位相同、快 13–20%（单 entry），可以做成引擎开关，估计端到端约 2%。
2. 140T 上 Q6_K 每多一列的成本主要在激活这一步；Q4_K 的激活和占 12–15%；两个 Q6_K 预读候选都更慢。
3. 新线索：引擎的 64 位寻址选项让稠密内核多出很多指令和溢出，开发机上去掉它稠密快 7–24%。140T 上的代价没测；去掉它要先解决超过 4 GiB 的专家缓存。

## 7. 下一步（需要你决定）
1. **在 140T 上测 64 位寻址的代价**：用现成工具（`kern_ablate`、`gr_bench`、`moe_probe`）各按两种链接选项编译，比较 MoE、稠密、hc 读，不改引擎，约 30 分钟。
   同时开发机查清哪些内核会读到超过 4 GiB 处。代价大就下一轮做引擎（默认关，逐位相同，端到端核对）。
2. **MoE gate/up 用 10 的 `slm` 写法做成引擎开关**（IQ3_XXS、IQ3_S、IQ2_XXS、IQ2_XS），`moe_probe` 和端到端在 140T 上测，估计约 2%。
3. **Q4_K/Q5_K 的激活和每窗口算一次**（逐位相同），在 140T 上和现状比。
